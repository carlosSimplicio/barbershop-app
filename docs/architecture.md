# Arquitetura

## Monorepo e responsabilidades

- Use `frontend/` e `backend/` como aplicações separadas no monorepo.
- O frontend consome a API REST sem depender de detalhes internos do backend.
- O backend concentra regras, validação, autorização e persistência.
- Mudanças de endpoint devem manter OpenAPI, implementação Go e consumo TypeScript alinhados.

## API contract-first

- A API usa o prefixo `/api/v1`.
- `backend/openapi/openapi.yaml` é a fonte da verdade.
- Altere primeiro o OpenAPI, regenere os artefatos e depois ajuste implementação e consumidores.
- Use `oapi-codegen` para modelos, interfaces e boilerplate Gin.
- Use `openapi-typescript` para os tipos do frontend.
- Mantenha um wrapper pequeno sobre `fetch`; não adicione outro cliente HTTP sem necessidade demonstrada.
- Código gerado não é editado manualmente. A automação deve detectar artefatos desatualizados.
- Geração não substitui validação em runtime, autenticação, autorização ou regras de negócio.

### Erros

- Use um formato único com código estável, mensagem em `pt-BR` e `request_id`.
- Erros de validação incluem detalhes estruturados por campo.
- O frontend decide pelo código, não pelo texto traduzido.
- Use status HTTP coerentes e documente respostas no OpenAPI.
- Não exponha stack traces, SQL, segredos, nomes internos ou infraestrutura; detalhes técnicos ficam nos logs correlacionados.

## Backend

- Use Go, Gin, PostgreSQL, `pgx/v5`, `sqlc` e Goose.
- Organize por Vertical Slice Architecture, agrupando cada capacidade ou caso de uso.
- Quando um domínio reunir fluxos independentes com lógica própria, organize-os em subpacotes por fluxo, como `auth/password_recovery`, `onboarding/registration` e `onboarding/email_confirmation`. Mantenha contratos, handlers e adaptadores compartilhados no pacote raiz quando dependerem de tipos ou estado internos comuns.
- Um slice pode conter handler, entrada/saída, validação, caso de uso e persistência necessários ao fluxo.
- Cadastro e edição de estabelecimento compartilham as validações puras `establishment.IsNameValid` e `establishment.IsTimeZoneValid`; normalização e tradução para erros de cada fluxo permanecem nas suas bordas.
- Evite grandes diretórios horizontais globais de handlers, services e repositories.
- Mantenha regras testáveis sem Gin, `pgx`, rede ou banco reais. A verificação de recuperação de senha decide elegibilidade, expiração, uso único e diferença da nova senha no caso de uso `auth/password_recovery`; o store recebe um preparador de hash, executa-o após bloquear usuário e token nessa ordem e só então persiste consumo, credencial e revogações atomicamente. O adaptador não recebe a nova senha nem o gerenciador de criptografia.
- Gin fica na borda HTTP; `pgx` e `sqlc`, na borda de persistência. Os handlers autenticados reutilizam `auth.RequirePrincipal` para obter a identidade já validada pelo middleware e emitir o mesmo `401` quando ela estiver ausente; papel, tenant e propriedade continuam sendo validados pelos casos de uso.
- Compartilhe apenas abstrações de domínio estáveis ou necessidades transversais reais; evite utilitários genéricos.
- Não adote CQRS formal, command/query bus, mediator ou event bus sem necessidade concreta.

### Estratégia de testes

- Mantenha testes unitários rápidos para regras de negócio, validações e recusas que possam ser verificadas sem infraestrutura real.
- Cubra os fluxos entregues do backend também com testes de integração black-box na fronteira HTTP, atravessando roteamento Gin, middleware, serviços, código `sqlc`, transações e constraints do PostgreSQL.
- Execute a integração em PostgreSQL descartável provisionado por Testcontainers, usando a mesma versão fixada para o projeto e aplicando as migrations Goose reais. Cada teste deve começar com dados isolados e determinísticos.
- Use `httptest` com TLS para preservar o comportamento dos cookies `Secure`. Substitua somente dependências externas ao backend, como o transporte de e-mail, por fakes locais controlados; não substitua banco, stores ou casos de uso nos testes de integração.
- Mantenha a suíte de integração sob a build tag `integration`. Testes unitários não exigem Docker; a suíte de integração e o gate de pull request exigem Docker disponível.
- Não adote testes E2E nem integração de frontend sem nova decisão. Evite duplicar nos testes de integração todas as combinações já protegidas unitariamente; priorize jornadas reais, contratos entre camadas, persistência, autorização e invariantes transacionais.

## Banco de dados

- Escreva SQL nos arquivos de entrada do `sqlc` e regenere o código Go após alterações.
- Não introduza ORM ou outro driver PostgreSQL em paralelo.
- A migration `00005_professionals.sql` cria `professionals` como perfil do usuário profissional. `user_id` é a identidade única; a chave estrangeira composta `(user_id, establishment_id)` impede associar o perfil a outro estabelecimento. As queries para inserir usuário, credencial e perfil e para listar por estabelecimento com paginação já existem; cadastro e listagem estão disponíveis pela API e pela página do painel.
- A migration `00006_establishment_settings.sql` adiciona descrição, endereço, telefone de contato e limites opcionais ao estabelecimento, além de `establishment_social_links`, ordenada por `position` e pertencente ao tenant. Os limites são inteiros; `NULL` significa sem restrição. `GET` e `PATCH /establishment/settings` são exclusivos ao proprietário; o PATCH preserva campos omitidos, permite limpar campos opcionais com `null` e substitui links de forma transacional. Valide no backend os limites de texto, links, URLs e valores dos limites; não os replique como regras de negócio em `CHECK` constraints. A aplicação dos limites aos fluxos de agendamento e cancelamento permanece pendente.
- A migration `00007_establishment_operational_lock.sql` adiciona `establishments.operational_data_started_at`, inicialmente nulo. Antes de alterar o fuso ou gravar o primeiro agendamento, bloqueio ou lançamento financeiro, a transação deve bloquear a mesma linha do estabelecimento com `LockEstablishmentOperationalWrite`. O fluxo operacional grava o registro e preenche o marcador com o instante da primeira gravação na mesma transação; se o chamador não fornecer um instante, a query usa `statement_timestamp()`. O `PATCH /establishment/settings` usa esse bloqueio e só altera `time_zone` enquanto o marcador continua nulo. O `FOR UPDATE` serializa os fluxos concorrentes; nenhuma configuração pode limpar o marcador. A integração do marcador aos futuros endpoints operacionais permanece pendente.
- A migration `00008_establishment_logos.sql` cria `establishment_logos` para metadados, hash SHA-256 e chave lógica estável do objeto, e adiciona `establishments.logo_id`, inicialmente nulo. Uma FK composta `(establishments.id, establishments.logo_id)` referencia `(establishment_logos.establishment_id, establishment_logos.id)` e impede associação cruzada entre tenants mesmo em gravações SQL diretas. Criação dos metadados e atualização do logo atual ocorrem na mesma transação, usando queries `sqlc` com o executor transacional; a leitura do logo atual sempre parte do estabelecimento. A query de associação recusa `NULL` para que a aplicação não remova um logo já associado; substituições apontam para novos metadados. A chave é gerada pela aplicação: no adaptador local é uma referência relativa, e em um futuro adaptador S3 é a chave do objeto. Não persista caminhos absolutos, nome de bucket ou URLs do provedor.
- Modele a oferta de serviços como uma associação explícita entre profissional e serviço, limitada ao mesmo estabelecimento.
- Mantenha preço e duração no serviço, não na associação com o profissional; somente a comissão pode possuir uma regra específica para esse par.
- Persista snapshots de preço e duração no agendamento; alterações posteriores no catálogo não recalculam agendamentos existentes.
- Valide a associação ativa ao consultar disponibilidade e novamente ao criar, reagendar ou registrar um atendimento sem agendamento; não confie apenas nas opções exibidas pelo frontend.
- Use UUIDs aleatórios e não sequenciais; gere-os com fonte segura e trate-os como opacos.
- UUID não substitui autorização ou isolamento de tenant.
- Toda alteração de schema usa migration Goose nova, pequena e determinística.
- Não modifique migrations que possam ter sido executadas em outro ambiente.
- Use transações quando uma operação precisar preservar invariantes entre múltiplas escritas.
- Use constraints do PostgreSQL para integridade estrutural, como nulabilidade, referências, unicidade, cardinalidade, isolamento relacional e ordenação temporal genérica. Regras de negócio que podem evoluir — formatos e palavras reservadas, limites de produto, papéis permitidos, durações exatas e transições ou imutabilidade de domínio — pertencem ao backend Go e aos seus testes, não a `CHECK` constraints ou triggers.

- A migration `00009_services.sql` persiste `services` com UUID, tenant, nome, centavos inteiros, duração em minutos, estado e datas. A FK preserva o estabelecimento e a chave composta permite referências futuras no mesmo tenant. Nome não é único, limites de produto pertencem ao Go e serviços não iniciam o marcador de dados operacionais. As queries do catálogo enumeram suas colunas em `SELECT` e `RETURNING`, preservando a projeção esperada pelos adaptadores quando o schema evoluir.

## Catálogo de serviços

- O slice `internal/services` implementa cadastro, listagem, consulta individual, edição parcial e estado ativo. Na composição da API e da suíte de integração, store e caso de uso são instanciados em variáveis próprias antes de criar o handler. Todos os endpoints derivam o tenant do `Principal` e autorizam somente `owner`. Escritas exigem origem confiável, CSRF e `entitlements.Service.RequireWrite`; rotas públicas e protegidas por CSRF usam listas de regras com caminho exato ou regex e o mesmo matcher. A lista CSRF inclui os caminhos parametrizados com UUID e `/status`, aplicados somente a métodos de escrita.
- `POST /services` recebe nome, `price_cents` inteiro e duração opcional; omitida ou nula usa 30 minutos. Nome com caractere NUL é recusado pela validação compartilhada de cadastro e edição com `400` e `invalid_name`, antes de chegar ao PostgreSQL. Cria serviço ativo e retorna `201` com ID, nome normalizado, preço, duração e estado.
- `GET /services` lista ativos e inativos por criação e ID decrescentes. `limit` padrão é 20, máximo 100; `offset` padrão é 0, máximo 2.147.483.647. O painel nomeia o tamanho da página e o limite de offset em constantes, derivando deles os avanços e recuos. A query busca `limit + 1` para `has_more`; resposta inclui `can_write`, calculado pelo componente central. Trial ausente ou expirado mantém leitura e retorna `false`; falha de infraestrutura permanece erro.
- `GET /services/{service_id}` retorna ativo ou inativo no tenant da sessão. UUID inválido recebe `400`; ID ausente ou de outro tenant recebe o mesmo `404`. A leitura permanece disponível sem trial ativo.
- `PATCH /services/{service_id}` altera somente nome, preço e duração recebidos, em SQL atômico filtrado por ID e tenant. Campos omitidos são preservados; duração nula aplica 30 minutos; nome/preço nulos e corpo sem campos são recusados. O handler mantém os campos do PATCH como `json.RawMessage` na primeira leitura para distinguir ausência de `null`; a segunda decodificação valida o tipo de cada campo e produz o erro de campo correspondente. Ponteiros no input representam valores opcionais; a persistência recebe valores concretos somente após a validação. Identidade e estado ativo permanecem fora dessa operação, preservando alterações concorrentes de outros campos.
- `PUT /services/{service_id}/status` recebe `active` booleano obrigatório e define o estado de forma idempotente. Preserva os demais dados, inclusive alterações concorrentes, e não existe endpoint de exclusão física. O catálogo ainda não integra associação profissional-serviço, agenda ou financeiro; contagem de agendamentos afetados e alertas serão implementados com a agenda.
- `/painel/servicos` usa `SessionGuard` de proprietário, `OwnerPanelShell`, `OwnerPanelPage` e os componentes existentes do design system. Clientes tipados usam `apiFetch` e os tipos gerados, abortam consultas e mutações ao desmontar e descartam respostas obsoletas por identidade ou seleção. `can_write` controla a conveniência da interface; a API revalida cada escrita.
- Preços são formatados e convertidos com aritmética inteira via `BigInt`. O campo BRL compõe `Field` e `AffixedInput`, com exemplos na referência do design system. Cadastro e edição compartilham os campos e o CSS Module `components/services/service-form.module.css` para o painel, espaçamento e largura do formulário; estilos de ações específicas permanecem no componente correspondente. O modelo do formulário recusa excesso de casas sem arredondar. Erros são apresentados por códigos locais e recebem foco depois que os controles são reabilitados. Cadastro, edição e mudança de estado compartilham a classificação de respostas em `service-operation-result`, incluindo sessão ausente, recurso ausente, modo somente leitura, erros de campo e resultado incerto; mensagens e transições da interface permanecem em cada componente.
- O cadastro confirma sucesso antes de recarregar a primeira página da lista; falha dessa recarga não desfaz a confirmação. Resultado ambíguo não provoca reenvio automático e orienta conferir a lista.
- A edição carrega o registro individual e envia apenas campos alterados. Após resultado ambíguo, bloqueia envio até nova consulta confirmada; a reconciliação compara com o baseline anterior, preserva campos editados e atualiza os demais com o GET atual. Isso evita reenviar valores antigos não editados. O editor propaga o registro persistido à lista após cada GET ou PATCH confirmado, por um callback estável que não reinicia a consulta ao renderizar o catálogo. Cancelar retorna o foco à ação de origem ou ao catálogo.
- Ativação/desativação pede confirmação na própria página e envia o estado desejado explicitamente. Resultado ambíguo exige consulta individual antes de outra tentativa, sem repetir a escrita automaticamente. A resposta confirmada atualiza a linha; o editor aberto recarrega e reconcilia o mesmo serviço. Um contador acompanha as operações pendentes, inclusive consultas de reconciliação simultâneas. Enquanto houver uma operação do catálogo em andamento, a interface bloqueia novos envios, paginação e atualização da lista para preservar os controles da operação atual.

## Arquivos públicos

- Armazene logos em um volume persistente local da VPS no MVP, montado em `LOGO_STORAGE_DIR` (`/var/lib/barbershop/logos` no Compose).
- O backend controla upload, validação e associação do arquivo ao estabelecimento.
- Aceite somente PNG, JPEG e WebP com tamanho máximo de 2.097.152 bytes e dimensões positivas de até 4.096 × 4.096 pixels; rejeite SVG no MVP.
- `establishment.ValidateLogo` limita a leitura a 2.097.153 bytes para detectar excesso, identifica o formato pelo conteúdo, inspeciona as dimensões antes da decodificação completa e recusa conteúdo truncado ou incompatível. Tamanho, tipo MIME, dimensões e SHA-256 retornados são derivados dos bytes validados; nome original e `Content-Type` do cliente não determinam os metadados.
- O decoder WebP usa `golang.org/x/image/webp` na versão fixa `v0.47.0`, pois o pacote padrão de imagens do Go não fornece decoder WebP. PNG e JPEG usam os decoders da biblioteca padrão. A dependência é somente de decodificação e tem licença BSD-3-Clause.
- Gere nomes internos não previsíveis; nunca use diretamente o nome enviado pelo usuário como caminho.
- Armazene no PostgreSQL somente metadados e uma chave lógica estável gerada pela aplicação. No storage local ela identifica o objeto relativamente à raiz configurada; em S3 poderá ser usada como object key. Não persista caminhos absolutos da VPS, nome de bucket nem URLs de provedor ou URLs assinadas.
- Não permita que caminhos fornecidos pelo cliente determinem onde um arquivo será lido ou gravado.
- `establishment.ObjectStorage` define escrita e leitura por streams e remoção por chave opaca UUID v4 gerada pela aplicação. Seus erros são independentes do provedor: `ErrInvalidObjectKey`, `ErrObjectNotFound`, `ErrObjectAlreadyExists` e `ErrStorageFailure`; remover objeto ausente é sucesso idempotente. A mensagem de falha não inclui caminho local; a causa fica disponível para inspeção interna.
- `platform/storage.LocalStore` implementa esse contrato sem expor caminhos aos casos de uso. Converte a chave UUID em um nome dentro de `LOGO_STORAGE_DIR` e usa `os.Root` para impedir que caminhos ou links simbólicos escapem da raiz. A escrita usa temporário restrito ao processo, sincroniza e fecha o conteúdo antes de criar atomicamente o objeto final sem sobrescrita; conteúdo incompleto não pode ser aberto. O backend inicializa o adaptador no startup e verifica acesso de escrita e remoção à raiz; `PUT /establishment/logo` consome o adaptador pela interface.
- `PUT /establishment/logo` exige origem confiável, CSRF, papel `owner` e direito de escrita centralizado. O corpo multipart completo é limitado a 2 MiB mais 64 KiB de envelope antes do parse; há exatamente um campo `file`, limitado a 2 MiB e validado por `establishment.ValidateLogo`. Extensão, nome original e `Content-Type` da parte não determinam tipo nem metadados. O caso de uso grava o conteúdo validado sob chave UUID v4 e então cria metadados e associa o novo logo numa transação com bloqueio da linha do estabelecimento. Falha confirmada compensa o novo objeto; erro de confirmação consulta o objeto atualmente associado antes de qualquer remoção e preserva o novo arquivo se o resultado continuar incerto. O objeto anterior só é removido após a associação nova ser confirmada; suas linhas antigas de metadados permanecem sem associação, enquanto falhas de compensação geram eventos operacionais sem dados sensíveis. A resposta `204` não revela nome original ou chave. O upload deixa `is_complete` verdadeiro quando há logo; `is_publishable` continua condicionado ao slug não reservado. Não existe operação para remover o logo.
- Casos de uso de upload dependem apenas de `establishment.ObjectStorage`; filesystem, diretórios e tipos de provedores ficam nos adaptadores. Uma implementação S3 futura deve manter o contrato e reutilizar a chave UUID como object key.
- `GET /public/establishments/{slug}/logo` resolve a elegibilidade pelo serviço central `PublicEstablishmentResolver`, que recusa slugs ausentes, inválidos ou reservados e estabelecimentos sem nome ou logo atual. A consulta subsequente vincula `establishment_id`, slug atual e `logo_id`; somente a chave lida do PostgreSQL é passada a `ObjectStorage.Open`. A resposta usa MIME e tamanho persistidos, `X-Content-Type-Options: nosniff`, `ETag` forte derivado do SHA-256 e `Cache-Control: public, no-cache`. `If-None-Match` pode retornar `304` sem corpo; depois de uma substituição, o ETag muda e o mesmo URL entrega o novo conteúdo. A leitura pública não depende do trial e não expõe a chave ou caminhos do adaptador.

## Multi-tenancy e página pública

- No MVP, a URL canônica é `/{establishment_slug}` no domínio principal.
- O slug é único e fica armazenado no estabelecimento; não armazene a URL completa.
- O proprietário informa o slug durante o cadastro. Valide formato, unicidade e palavras reservadas no backend antes de criar o estabelecimento.
- Aceite somente letras minúsculas ASCII, números e hífens, com 3 a 63 caracteres e sem hífen no início ou no fim.
- Valide o valor informado em vez de transformá-lo silenciosamente; o frontend deve explicar o formato antes do envio.
- Trate o slug como imutável no MVP e não ofereça endpoint ou ação de interface para alterá-lo.
- Reserve os segmentos de rota da plataforma `admin`, `api`, `assets`, `cadastro`, `confirmar-email`, `design-system`, `login`, `painel`, `recuperar-senha`, `redefinir-senha` e `testes`. `api` cobre o prefixo `/api/v1`; `painel` protege sua árvore de páginas. O alfabeto válido do slug já exclui caminhos técnicos como `/_next`.
- Centralize a lista em `establishment.IsPublicSlugReserved` para o cadastro e para as decisões de elegibilidade. Preserve slugs legados em conflito: a consulta de configurações sinaliza o conflito e o resolvedor público recusa a publicação naquele caminho até resolução operacional explícita. Não renomeie slugs automaticamente.
- Centralize a resolução do estabelecimento; domínio e consultas não dependem diretamente do formato da URL.
- Prepare o resolvedor para futuramente aceitar `{establishment_slug}.barbershop-app.com`.
- Não publique caminho e subdomínio simultaneamente como canônicos. Em migração futura, redirecione permanentemente os caminhos antigos.
- Toda consulta autenticada ou pública inclui explicitamente o estabelecimento resolvido.
- `GET /establishment` deriva o estabelecimento exclusivamente do `Principal` autenticado e não aceita identificador de tenant como autoridade em path, query ou corpo. A resposta limita-se a identificador, nome, slug, fuso IANA e trial; seus limites são instantes UTC, enquanto o fuso persistido continua sendo a autoridade para regras e apresentação locais.
- `GET /establishment/settings` é exclusivo ao papel `owner` e também deriva o tenant somente do `Principal`. Lê perfil, logo e links ordenados numa única consulta SQL, preservando um snapshot consistente diante de atualizações concorrentes. Retorna os dados públicos opcionais, links ordenados, limites, metadados públicos do logo e os estados `time_zone_editable`, `can_write`, `slug_conflict`, `is_complete` e `is_publishable`. `can_write` reutiliza `entitlements.Service`; a leitura continua permitida após expiração do trial. O fuso só é indicado como editável quando `operational_data_started_at` estiver nulo e o componente central autorizar escritas. Slugs legados reservados são sinalizados e não são considerados publicáveis. `is_publishable` indica que nome, logo atual e slug utilizável permitem publicação. O perfil e o logo públicos são servidos pelas rotas descritas abaixo, inclusive após a expiração do trial. A resposta das configurações expõe somente metadados validados do logo; a URL pública por slug é nula quando o estabelecimento não é publicável. Nunca exponha a chave lógica de storage, caminho interno, nome original ou credenciais. `GET /establishment` mantém seu contrato enxuto e independente.
- `PATCH /establishment/settings` exige origem confiável, CSRF, papel `owner` e direito de escrita centralizado. Campos omitidos preservam valores; `null` limpa dados opcionais e limites; lista vazia ou nula limpa os links. Nome, descrição/endereço, telefone, links e limites são validados no backend. O telefone brasileiro é persistido normalizado. A alteração de fuso e a verificação de `operational_data_started_at` usam o mesmo bloqueio transacional dos futuros primeiros registros operacionais; um fuso diferente é recusado depois do marcador, enquanto repetir o fuso atual é permitido. O OpenAPI declara access cookie, cookie CSRF e header CSRF no mesmo requisito de segurança. O PATCH não aceita slug nem marcador no corpo e atualiza dados e links em uma transação. Com trial expirado, responde `read_only` sem alterações. A configuração entregue ainda não aplica limites nos fluxos de agendamento.
- A API também expõe `PUT /establishment/logo` com autenticação, CSRF e `multipart/form-data`; a sessão define o tenant e somente owner com trial gravável pode enviar ou substituir o logo.
- A API expõe `GET /public/establishments/{slug}/logo` sem autenticação para leitura somente de logos publicáveis. A exceção do middleware é limitada a `GET` e ao caminho exato de cada rota pública por slug; não libera métodos de escrita, subcaminhos ou outras rotas.
- A API expõe `GET /public/establishments/{slug}` sem autenticação para perfis publicáveis. O resolvedor compartilhado recusa slug ausente ou reservado e considera publicável somente o estabelecimento com nome, slug utilizável e logo atual associado. A resposta contém nome, slug, URL relativa do endpoint do logo e, quando preenchidos, descrição, endereço, telefone e links ordenados; não inclui ID, dados de trial, fuso ou limites de agenda. A consulta de perfil não depende do trial e não oferece disponibilidade nem operações de agendamento. A exceção de autenticação cobre somente `GET` nesse caminho exato.
- A página canônica `/{slug}` é renderizada por Server Component, que consulta diretamente a API Go usando `API_INTERNAL_URL`, sem cookies, BFF, Route Handler ou Server Action. `PUBLIC_APP_URL` fornece a origem HTTPS dos metadados canônicos. Ambas as origens são validadas no startup Node e permanecem em módulo protegido por `server-only`; o Compose fornece as duas ao frontend em runtime. A consulta usa `cache: no-store`, timeout de 5 segundos e recusa redirecionamentos; página e metadados compartilham a leitura durante a requisição. Apenas `404` produz página ausente; falhas temporárias preservam a distinção e oferecem nova tentativa com `retry` do Next.js, que solicita um novo render no servidor. Nome e logo são obrigatórios, opcionais preenchidos aparecem como texto simples, e o logo usa diretamente seu endpoint revalidável, sem cache do otimizador de imagens. A página segue os tokens do design system, prioriza telas pequenas e continua disponível após expiração do trial. A jornada de agendamento permanece pendente.

## Autenticação

- Proprietários e profissionais usam e-mail e senha; a API usa JWT.
- O e-mail de login é único em toda a plataforma, comparado de forma normalizada e sem diferenciar maiúsculas de minúsculas; não use o estabelecimento para desambiguar contas.
- O e-mail de login é imutável no MVP; não ofereça endpoint ou ação de interface para alterá-lo.
- Nunca armazene senha em texto puro nem registre senhas ou tokens.
- Backend e validação de conveniência do frontend aceitam senhas de 8 a 32 pontos de código e recusam a união de Unicode `White_Space`, controles (`Cc`), formatação (`Cf`) e `Default_Ignorable_Code_Point`. Isso inclui `U+FEFF`, `U+200B`, joiners, marcadores de direção, seletores de variação e fillers invisíveis; sequências de emoji que dependam desses marcadores também são recusadas. Acentos combinantes normais e símbolos visíveis continuam permitidos. O Go usa `unicode.IsSpace`, `unicode.IsControl` e as tabelas `Cf`, `Other_Default_Ignorable_Code_Point` e `Variation_Selector`; o frontend usa as propriedades Unicode equivalentes. A senha é recusada como recebida, sem trim, remoção, substituição ou normalização. A ampliação considera inexistentes credenciais anteriores; não há migração de senhas.
- A regra se aplica ao cadastro do proprietário, senha temporária do profissional, login, troca obrigatória e redefinição por recuperação.
- Não exija combinações obrigatórias de maiúsculas, minúsculas, números ou símbolos e não imponha troca periódica.
- Não consulte listas de senhas comuns ou credenciais comprometidas no MVP.
- Armazene senhas com Argon2id, salt único por senha e parâmetros centralizados e ajustáveis; nunca use hash rápido ou criptografia reversível.
- Aplique limitação progressiva às tentativas de login usando, no mínimo, a combinação de IP e e-mail normalizado.
- Não bloqueie a conta permanentemente. Use janelas temporárias, responda de forma genérica e não revele se o e-mail está cadastrado.
- Retorne `429` e `Retry-After` quando aplicável e estenda a mesma proteção aos fluxos de confirmação e recuperação.
- Não implemente autenticação em dois fatores no MVP; preserve o modelo de autenticação de forma que ela possa ser adicionada posteriormente sem alterar as regras de domínio.
- Use access JWT com expiração fixa de 15 dias, sem refresh token ou renovação por uso. `auth.SessionLifetime` centraliza essa duração para o emissor JWT, criação de sessões no login/confirmação/troca de senha e `Max-Age` dos cookies access e CSRF.
- Transporte o access JWT em cookie `HttpOnly`, `Secure` e `SameSite=Strict`, com escopo mínimo; o CSRF fica em cookie legível pelo frontend.
- Não use `localStorage` ou `sessionStorage` para tokens.
- Cada access JWT identifica uma sessão persistida, que pode ser revogada imediatamente no backend.
- Proteja mutações contra CSRF e valide origem e autorização.
- JWT contém apenas claims necessárias: usuário, sessão, estabelecimento, papel, expiração e versão de credencial.
- Reset de senha invalida credenciais previamente emitidas.
- Desativar um usuário revoga suas sessões, incrementa sua versão de credencial e faz o backend rejeitar imediatamente access tokens ainda não expirados.

### Contrato de sessão

- A API expõe `POST /auth/register`, `POST /auth/email-confirmation`, `POST /auth/email-confirmation/verify`, `POST /auth/password/recovery`, `POST /auth/password/recovery/verify`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/password/change`, `GET /establishment`, `GET /establishment/settings`, `PATCH /establishment/settings`, `PUT /establishment/logo` e `GET /public/establishments/{slug}/logo` sob `/api/v1`.
- `POST /auth/register` é público, mas mantém a allowlist estrita de `Origin`. Ele valida no backend nome, slug, fuso IANA, e-mail e senha; cria estabelecimento, usuário `owner`, credencial e primeira confirmação em uma única transação; e não cria trial.
- O cadastro responde `202 Accepted` depois do commit. O envio da confirmação ocorre diretamente pelo serviço interno após a transação; falha de transporte é registrada apenas como evento operacional, sem e-mail, token ou link, e não transforma o cadastro persistido em erro HTTP.
- Conflitos de e-mail global e slug único retornam `409` com erro associado ao campo correspondente. A limitação progressiva do cadastro usa escopo próprio e chaves HMAC separadas para IP e e-mail normalizado, sem persistir esses identificadores em claro.
- A reserva dos eventos de rate limiting pertence à infraestrutura compartilhada em `internal/platform/ratelimit`; autenticação e onboarding recebem esse store explicitamente e não reutilizam stores de outro slice. O store serializa concorrentemente cada chave HMAC com advisory locks transacionais, verifica todas as dimensões e grava seus eventos na mesma transação, impedindo que requisições simultâneas ultrapassem o limite. No login, a reserva é removida quando a tentativa não representa credencial inválida, preservando a contagem exclusiva de falhas.
- `POST /auth/email-confirmation` é público, mantém validação estrita de `Origin` e recebe o e-mail somente no corpo. Para qualquer e-mail válido, conta inexistente, owner já confirmado e nova confirmação emitida recebem o mesmo `202 Accepted` sem corpo.
- Quando há owner ativo ainda não confirmado, a substituição bloqueia e revalida sua elegibilidade, invalida tokens ativos e persiste um novo token de 24 horas antes do envio. Mudança concorrente de elegibilidade encerra a solicitação sem novo token. Falha de transporte após a persistência não altera o `202` e gera somente evento operacional sem e-mail ou token.
- Confirmação e recuperação reutilizam o hook `useTransactionalLinkToken`, que captura o token somente do fragmento, remove fragmento e query antes de liberar consumidores e preserva a captura em memória sob Strict Mode. Falha ao limpar a URL impede montar Provider ou formulário.
- A mensagem usa `/confirmar-email#token=...`: o fragmento não participa da requisição HTTP. A interface extrai o token, remove o fragmento e a query do histórico antes de qualquer navegação ou chamada de API e o envia exclusivamente no corpo de `POST /auth/email-confirmation/verify`. A verificação de uso único é iniciada uma vez mesmo sob Strict Mode; token ausente ou resposta inválida/expirada recebe mensagem própria, sem expor o valor.
- O rate limiting da solicitação de confirmação usa escopo próprio, IP e e-mail normalizado e é registrado antes de consultar a conta, preservando o mesmo tratamento de abuso independentemente de sua existência.
- A proteção anti-enumeração atual uniformiza status e corpo, mas não garante tempo constante: o SMTP síncrono pode tornar solicitações elegíveis de confirmação ou recuperação mais lentas. Esse risco é aceito nesta etapa; não há outbox nem sessão restrita antes da confirmação, e eventual endurecimento de latência exige uma decisão arquitetural posterior.
- `POST /auth/email-confirmation/verify` é público, exige `Origin` confiável e recebe o token somente no corpo. A transação bloqueia primeiro o owner e depois o token, na mesma ordem usada pelo reenvio, para evitar deadlock; então valida expiração e estado na aplicação, confirma o e-mail, consome o token e cria o único trial exato de 14 dias e uma sessão com prazo fixo de 15 dias. Replay, token substituído, expirado ou inexistente produzem o mesmo erro; access JWT e CSRF são preparados antes do commit, de modo que uma falha de emissão reverta a transação, e então são enviados nos cookies seguros.
- Confirmações persistem apenas o hash SHA-256 do token aleatório de 256 bits, sua expiração e estados de consumo ou invalidação. Trials ficam separados de assinaturas e preservam proprietário, estabelecimento e a janela imutável `[confirmed_at, confirmed_at + 14×24h)` com unicidade para ambos.
- Access JWTs usam Ed25519/EdDSA, incluem `kid` no header e são validados por um keyring de chaves públicas. A chave privada ativa e as chaves públicas anteriores são configuração exclusiva do backend.
- As claims são limitadas a usuário, ID da sessão, estabelecimento, papel, expiração e versão da credencial. Em cada requisição autenticada, o backend consulta a sessão não revogada e não expirada junto ao usuário atual e compara usuário, estado, tenant, papel e versão. Tokens antigos sem ID da sessão são recusados.
- A configuração inicial do Argon2id usa `m=19456 KiB`, `t=2`, `p=1`, salt aleatório de 16 bytes e saída de 32 bytes em formato PHC. Os limites configuráveis não podem ficar abaixo desse perfil.
- Os dois cookies são host-only, `Secure` e `SameSite=Strict`, inclusive no desenvolvimento local. `__Secure-barbershop_access` usa `Path=/api/v1`, `HttpOnly` e `Max-Age` de 15 dias; `__Secure-barbershop_csrf` usa `Path=/`, `Max-Age` de 15 dias e pode ser lido pelo frontend somente para envio no header `X-CSRF-Token`.
- Mutações validam uma allowlist exata de `Origin`. Logout e troca de senha também exigem igualdade entre cookie e header CSRF e assinatura válida do token. O navegador descarta o cookie CSRF após 15 dias; o token não contém um prazo assinado.
- O rate limiting de login usa chaves HMAC separadas para IP e e-mail normalizado, sem persistir esses valores na tabela de tentativas. Depois de 5 falhas em 15 minutos, 10 em 1 hora ou 20 em 24 horas, novas tentativas recebem `429` e `Retry-After` pela maior janela ativa.
- Várias sessões por usuário são permitidas. Cada uma expira 15 dias após a criação, sem prorrogação por uso; logout revoga somente a sessão indicada pelo access JWT válido. Access ausente ou inválido ainda permite logout idempotente com CSRF válido, limpando os cookies sem revogar uma sessão não identificada.
- `transport.ts` envia as requisições com cookies, inclui CSRF quando solicitado e interpreta as respostas. `client.ts` avisa o `AuthProvider` quando qualquer requisição retorna `401`, sem renovar ou repetir a chamada. O Provider encerra a sessão local e a guarda redireciona para `/login`. Falhas de rede e `5xx` não são tratadas como logout. Consultas canceladas não notificam `401`; o Provider cancela a consulta de `/auth/me` após uma ação de sessão bem-sucedida ou um `401`. Não há Web Lock nem persistência de tokens ou estado em Web Storage.
- Nas rotas comuns de sessão, o `AuthProvider` fica no layout do grupo `(session)`, preservando a home estática sem consulta de autenticação. `/confirmar-email` é uma rota de bootstrap fora desse grupo: só monta uma instância do mesmo Provider depois de remover o fragmento e a query da URL, impedindo que a consulta inicial de `/auth/me` preceda a limpeza. O Provider consulta `/auth/me`, mantém somente identidade e estado transversal, distingue sessão ausente de erro temporário e expõe recarga e ações explícitas de login, confirmação, troca de senha e logout. Quando a ação retorna `AuthPrincipal`, ele aplica diretamente essa identidade sem uma segunda chamada a `/auth/me`; ações sem principal reconsultam a sessão. Uma resposta antiga da consulta de identidade não pode sobrescrever uma sessão alterada explicitamente. A guarda aceita sessão autenticada ou papel de `owner`, mantém conteúdo protegido oculto durante a descoberta e redireciona visitante para `/login` e profissional sem acesso ao painel para `/testes`. Login, confirmação e redirecionamento de proprietário já autenticado usam `/painel`; essa entrada consulta `GET /establishment/settings` e encaminha para `/painel/configuracoes` se `logo` for nulo ou `/painel/profissionais` se houver logo. Erros temporários da consulta mostram falha e permitem nova tentativa, sem confundir a falha com sessão ausente. A ausência do logo não bloqueia acesso direto às páginas do painel. Profissionais seguem para `/testes`. A casca reutilizável do painel tem navegação por teclado para Profissionais, Configurações e a área temporária `/testes`; identifica a rota atual com `aria-current` e não marca link ativo na página de entrada. `/cadastro` usa a guarda de visitantes.
- Um profissional com senha temporária pode consultar sua sessão, trocar a senha ou sair, mas não acessar recursos de domínio. Em `/testes`, o formulário de troca aparece somente quando `password_change_required` é verdadeiro, envia apenas `new_password` com CSRF e mapeia `invalid_password` e `password_unchanged` para o campo. A troca rejeita a mesma senha, revoga todas as sessões, incrementa a versão da credencial e reemite somente a sessão atual. Enquanto a troca está pendente, os botões de consulta ficam indisponíveis; depois de `204`, o frontend reconsulta `/auth/me`, remove o formulário e libera a consulta do estabelecimento apenas quando o principal atualizado não exigir mais a troca. Um `401` encerra a sessão local; a mutação não é repetida automaticamente.
- Em `/testes`, o logout envia `POST /auth/logout` com cookies e CSRF como ação explícita do Provider, inclusive para profissional com senha temporária. O botão bloqueia cliques simultâneos. O backend responde `204` e limpa access e CSRF após validação do CSRF, mesmo se o access estiver ausente ou inválido; essa resposta faz o Provider eliminar a identidade local e a guarda substituir a rota por `/login`, sem consultar `/auth/me` novamente. Um `401` também encerra a sessão local. Outras falhas, inclusive `500` ou resposta fora do contrato, preservam a identidade exibida e oferecem nova tentativa sem afirmar que os cookies foram removidos. O frontend não repete a mutação automaticamente.

### Retenção dos dados de autenticação

- Access JWTs e tokens CSRF não geram registros próprios; cada login cria uma linha em `auth_sessions`. Cada cadastro ou substituição elegível cria uma linha em `email_confirmations`; falhas de login e tentativas válidas de cadastro, confirmação ou recuperação criam eventos separados por dimensão em `auth_login_attempts`, com escopos independentes. Cada solicitação elegível de recuperação cria uma linha em `password_recovery_tokens` com somente o hash, expiração e estados de consumo ou invalidação, permitindo no máximo um token ativo por usuário. A verificação consome o token válido na mesma transação que altera a credencial e revoga as sessões do proprietário.
- `POST /auth/password/recovery` é público com `Origin` confiável obrigatório, recebe somente o e-mail, valida seu formato e limita tentativas por IP e e-mail normalizado no escopo `password-recovery` antes da busca. Apenas proprietário ativo com e-mail confirmado pode receber o link. A busca é global pelo e-mail único, e a elegibilidade é revalidada sob bloqueio de linha antes da substituição transacional. A resposta é `202` sem corpo para contas elegíveis, ausentes ou inelegíveis, inclusive quando o transporte de e-mail falha depois da persistência; `429` inclui `Retry-After`. Cada link novo invalida o anterior e expira em 1 hora.
- `POST /auth/password/recovery/verify` é público com `Origin` confiável obrigatório e recebe token e nova senha somente no corpo. O backend valida formato e expiração, revalida sob bloqueio que o usuário ainda é proprietário ativo com e-mail confirmado, e recusa senha igual à atual. A transação consome o token, grava o novo hash Argon2id, incrementa `credential_version` e revoga todas as sessões desse usuário. Token inexistente, expirado, substituído ou usado recebe o mesmo erro; sucesso responde `204`, sem nova sessão ou cookies. A interface de consumo do link orienta o retorno ao login após sucesso.
- A implementação atual não executa limpeza de sessões, confirmações de e-mail, tokens de recuperação ou eventos de rate limiting. A query de exclusão de eventos antigos existe, mas ainda não está ligada a uma rotina operacional. Essas tabelas poderão crescer sem limite quando seus fluxos gravarem dados e não devem ser consideradas prontas para operação prolongada em produção.
- A retenção deve remover eventos de rate limiting de todos os escopos depois da maior janela aplicável, atualmente 24 horas, acrescida de margem operacional; remover confirmações e tokens de recuperação consumidos, invalidados ou expirados somente depois da janela operacional definida; e remover sessões expiradas ou revogadas depois da janela operacional definida.
- Execute a limpeza em lotes limitados, com índices apropriados para os predicados de expiração e um único executor por vez.
- Monitore quantidade de linhas, tamanho total e idade do registro elegível mais antigo em `auth_sessions`, `email_confirmations`, `password_recovery_tokens` e `auth_login_attempts`. Confie no autovacuum para tornar espaço apagado reutilizável; não use `VACUUM FULL` como manutenção rotineira.

### Proprietário e profissional

- Proprietário confirma e-mail e recupera senha por link enviado por e-mail.
- Tokens de confirmação e recuperação são aleatórios, expiram, são de uso único e não ficam armazenados de forma utilizável após vazamento do banco.
- Respostas de recuperação não revelam se o e-mail existe; aplique rate limiting.
- Profissional não possui recuperação autônoma. O proprietário define uma senha temporária e a troca é obrigatória no próximo login.
- `POST /professionals` exige sessão de proprietário, `Origin` confiável, CSRF válido e direito de escrita do trial. O estabelecimento vem apenas do principal autenticado. O backend valida nome, e-mail e senha temporária, cria usuário `professional` ativo, credencial Argon2id e perfil na mesma transação, e responde `201` somente com identificador, nome, e-mail e estado ativo. E-mail duplicado em qualquer estabelecimento gera conflito no campo `email`; a senha não aparece em resposta nem logs.
- `GET /professionals` exige sessão de proprietário e deriva o estabelecimento do principal. A query filtra pelo tenant, ordena por criação decrescente com desempate pelo ID e consulta no máximo 101 registros para entregar até 100 por página e indicar `has_more`; `limit` padrão é 20 e `offset` padrão é 0. A resposta contém apenas identificador, nome, e-mail e estado ativo; lista vazia é `[]`, e a leitura permanece disponível após expiração do trial. `/painel/profissionais` consome essa resposta tipada e apresenta nome, e-mail e estado ativo com paginação. O formulário usa o cliente tipado para `POST /professionals`, envia CSRF e, após `201`, limpa a senha do estado, informa que ela não poderá ser recuperada e atualiza a lista. `email_unavailable` vira erro no campo de e-mail; falhas inesperadas não exibem mensagens brutas. A resposta `read_only` explica que a lista permanece disponível, mas cadastros são bloqueados sem trial ativo.
- Ao reativar um profissional, o proprietário deve definir uma nova senha temporária; nunca restaure a validade da senha ou das sessões anteriores.
- Até a troca, o profissional só pode consultar ou manter a sessão, definir uma nova senha ou encerrar a sessão; recursos de domínio permanecem bloqueados.
- A senha temporária nunca é recuperável ou armazenada em texto puro.

### E-mail transacional

- O provedor ainda não foi definido.
- Isole envio atrás de uma interface pequena; não adicione SDK de SMTP, SES, Resend ou outro provedor antes da decisão.
- Em desenvolvimento local, use SMTP com Mailpit para inspecionar mensagens de confirmação e recuperação sem enviar e-mails reais. O transporte usa um orçamento total de 10 segundos desde DNS/conexão até o encerramento SMTP, respeita um deadline anterior do chamador e fecha a conexão quando o contexto é cancelado.
- O Mailpit é uma dependência exclusiva de desenvolvimento e nunca é fallback para produção.
- Em produção, falhe de forma segura se o envio de e-mail necessário estiver habilitado sem um provedor real configurado.
- Não registre endereço completo, token, link de recuperação ou credenciais ao tratar falhas.
- Templates de confirmação e recuperação ficam versionados e em `pt-BR`.
- O template de recuperação é enviado pelo transporte configurado. O token aparece apenas no fragmento do link `/redefinir-senha#token=...`; a página limpa fragmento e query antes de montar o formulário ou qualquer link e envia token e senha somente no corpo de `POST /auth/password/recovery/verify`. Ela não monta o Provider de sessão nem autentica automaticamente. Falhas de transporte geram apenas evento operacional sem e-mail, token ou URL.

## Assinaturas da plataforma

- Modele assinatura e trial separadamente dos recebimentos dos atendimentos do estabelecimento.
- O cadastro não depende de uma assinatura ativa.
- Persista a utilização do trial separadamente da assinatura atual; nunca derive elegibilidade apenas da ausência de uma assinatura ativa.
- O MVP possui um plano comercial, mas não codifique a suposição de plano único em tabelas, regras ou contratos.
- Separe o conceito de plano das opções de preço e período de cobrança, permitindo vários preços ou durações para o mesmo conjunto de funcionalidades.
- Cadastre o preço mensal inicial como `BRL 20,00` no catálogo persistido ou em dados de inicialização versionados; não o espalhe como constante no código.
- Crie plano e preço iniciais por migration/seed idempotente e versionado.
- Não implemente perfil ou painel de administrador da plataforma no MVP; mudanças de catálogo são alterações controladas de seed/migration.
- Versione preços e preserve na assinatura a opção contratada, para que reajustes futuros não alterem silenciosamente contratos existentes.
- Modele adicionais como itens opcionais da assinatura, com preço e direitos próprios, sem adicionar colunas específicas para cada produto futuro.
- Centralize a resolução de direitos de acesso; não espalhe comparações de nome de plano ou adicional pela aplicação.
- Preserve em cada assinatura os identificadores e termos necessários para interpretar historicamente o que foi contratado.
- Não acople o domínio a um gateway específico enquanto o provedor de cobrança não estiver decidido.
- Defina uma interface de provedor de cobrança e implemente inicialmente um adaptador mockado.
- O mock não movimenta dinheiro nem coleta dados reais de pagamento e deve ser identificado claramente na interface e nos logs.
- Habilite o mock somente por configuração explícita nos ambientes autorizados; falhe de forma segura se produção exigir um provedor real ainda não configurado.
- Faça o mock simular de forma determinística os estados necessários para desenvolver assinatura, renovação, falha e cancelamento.
- A ação mockada de assinatura é idempotente: repetição da mesma solicitação não cria assinaturas ou períodos duplicados.
- Ao aprovar, registre início e fim do período contratado e conceda os direitos do plano pelo domínio de assinaturas, não diretamente pelo handler.
- A renovação mockada é manual e idempotente. Período ativo é estendido a partir do fim atual; assinatura expirada cria novo período a partir da reativação.
- Modele cancelamento ao fim do período separadamente de expiração imediata; direitos permanecem ativos até `current_period_end`.
- Centralize a política de acesso por assinatura: trial ou período ativo concede escrita; expiração preserva leitura e bloqueia mutações, exceto autenticação e assinatura/renovação.
- O componente `backend/internal/entitlements` consulta o trial persistido por estabelecimento e concede escrita somente do instante inicial inclusivo ao final exclusivo. Sem trial ou depois do término, retorna recusa de escrita; erro de consulta não concede acesso. `POST /professionals` já usa essa decisão. Ainda não há períodos de assinatura; os demais endpoints de domínio serão ligados ao componente quando forem entregues.
- `GET /professionals` é uma leitura autenticada e não consulta o direito de escrita, portanto continua disponível após o fim do trial.
- Aplique a política no backend e não apenas na interface. Todos os endpoints públicos de mutação da agenda devem respeitar o direito de acesso do estabelecimento.
- Expiração não altera estados nem remove agendamentos; apenas bloqueia suas mutações até a reativação.
- Estados, webhooks, idempotência e acesso por plano devem ser definidos antes de implementar a integração de cobrança.

## Frontend

- A home deslogada em `/` é uma landing page estática, renderizada no servidor e sem chamadas à API. `/cadastro` usa o layout de sessão e a guarda de visitantes, envia `POST /auth/register` pelo cliente tipado e mantém um estado de confirmação pendente após `202`, sem criar sessão ou iniciar o trial. Nesse estado, um componente reutilizável permite solicitar `POST /auth/email-confirmation` para o mesmo e-mail; ele nunca mostra a mensagem bruta do backend e apresenta o mesmo sucesso genérico para qualquer `202`. `/confirmar-email` monta primeiro uma fronteira que lê e elimina o fragmento; somente depois monta o Provider, verifica o token e, após sucesso, substitui a rota por `/painel`. `/login` usa a guarda de visitantes e `POST /auth/login` pelo cliente tipado, trata credenciais inválidas sem detalhes, oferece o mesmo reenvio após `email_confirmation_required` e sincroniza a sessão antes de direcionar proprietário a `/painel` ou profissional a `/testes`. `/painel` usa a guarda de papel `owner` e consulta `GET /establishment/settings` para encaminhar a Configurações quando não há logo ou a Profissionais quando há; falhas permitem nova tentativa e não afirmam ausência de sessão. O proprietário pode acessar `/painel/profissionais` diretamente mesmo sem logo. A página de Profissionais usa a mesma guarda e casca reutilizável com navegação para Profissionais, Configurações e `/testes`; permite cadastro pelo cliente tipado com CSRF, validação de conveniência e mensagens específicas sem texto bruto do backend. Após sucesso, limpa a senha temporária e atualiza a lista, que mostra nome, e-mail, estado ativo, carregamento, vazio, erro e paginação. `/testes` permanece acessível pela navegação do painel e usa a guarda autenticada, apresenta papel, identificadores e `password_change_required` sem e-mail ou tokens, e permite repetir `GET /auth/me` pelo Provider; falha temporária mostra opção de nova tentativa, e sessão ausente substitui a rota por `/login`. Uma seção separada consulta `GET /establishment` sem identificador de tenant no pedido, apresenta nome, slug, fuso e trial ausente, ativo ou expirado, e fica indisponível durante troca obrigatória de senha. A seção descarta respostas antigas após troca de identidade. Seções próprias permitem trocar a senha temporária quando exigido e encerrar a sessão. A lista aborta consultas obsoletas ao mudar de página ou identidade e ignora respostas antigas. Os tipos TypeScript gerados do OpenAPI permanecem sincronizados.
- `/login` oferece um link para `/recuperar-senha`. Essa rota usa a guarda de visitantes e um formulário com e-mail validado por conveniência; o cliente tipado envia `POST /auth/password/recovery` sem e-mail em path ou query. Qualquer `202` mostra o mesmo sucesso genérico e encerra o formulário para evitar novo pedido que invalidaria o link anterior. A interface trata `429`, erro de campo e falha de rede sem mostrar mensagens brutas.
- `/redefinir-senha` fica fora do layout que consulta `/auth/me`; uma fronteira cliente captura o token do fragmento e remove fragmento e query antes de montar formulário ou links. Token e nova senha seguem apenas no corpo do cliente tipado. A tela distingue link inválido ou expirado, senha inválida ou igual à atual e falha temporária; após `204`, mostra retorno ao login sem criar sessão.
- `/cadastro` e `/painel/configuracoes` reutilizam `BrazilianTimeZoneField`, que centraliza as quatro opções IANA brasileiras e seus rótulos locais. O cadastro usa `America/Sao_Paulo` se a detecção do navegador apontar para outro país ou falhar.
- Cadastro e Configurações reutilizam `EstablishmentSlugField`, com o prefixo visual `/` fora do valor do slug; o cadastro edita o campo e Configurações o desabilita.
- `BrazilianPhoneField` é uma primitiva do design system para telefones brasileiros; aplica máscara distinta para telefones fixos e celulares, limita o campo a 15 caracteres e converte números já persistidos com código do país para apresentação nacional.
- `/painel/configuracoes` usa `SessionGuard` de proprietário e `OwnerPanelShell`. O cliente tipado consulta `GET /establishment/settings` e envia por CSRF `PATCH /establishment/settings` somente para campos alterados; campos opcionais e limites vazios são enviados como `null`, e a lista vazia limpa links. A tela usa os estados `can_write` e `time_zone_editable` retornados pelo backend, oferece um seletor com quatro fusos brasileiros e seus nomes locais, e limita novos links sociais a Instagram, Facebook, X, YouTube, TikTok e LinkedIn com prefixo HTTPS fixo. Mapeia códigos de erro por campo sem exibir mensagens brutas, oferece nova tentativa após falha de leitura e aborta consultas/mutações obsoletas ao trocar identidade ou desmontar.
- O componente de configurações envia ou substitui o logo por `PUT /establishment/logo` usando `apiFetch`, `FormData` e CSRF; não define `Content-Type`, deixando o navegador criar o boundary. A pré-visualização ocupa o lugar da imagem atual e usa uma URL `blob:` liberada ao limpar ou substituir a seleção, concluir o envio ou desmontar. O proprietário pode limpar um arquivo ainda não enviado, sem remover o logo associado. O cliente atualiza `GET /establishment/settings` após `204`. Em falha confirmada, limpa o arquivo e a pré-visualização mesmo quando não havia logo anterior, restaurando a imagem publicada quando existir; para `5xx`, respostas fora do contrato ou falha de rede, consulta as configurações antes de concluir o resultado. Se essa consulta também falhar, mantém arquivo e pré-visualização e oferece atualizar o estado, bloqueando outro envio até a reconciliação. O componente impede uploads e atualizações simultâneas e desabilita mutações quando `can_write` é falso. Não há ação de remoção do logo publicado. O endereço `/{slug}` aparece quando `is_publishable` é verdadeiro; se a consulta falhar após um `204`, pode ser derivado do upload confirmado quando nome e slug sem conflito já estão persistidos.
- A interface de configurações separa o controle de sessão/consulta, o formulário de edição, o editor de redes sociais, o envio do logo e as transformações e validações puras do modelo do formulário.
- As páginas do painel do proprietário usam `OwnerPanelPage` para compartilhar o cabeçalho, a introdução e o espaçamento do conteúdo. Cada página mantém seus próprios formulários e cartões dentro dessa composição.
- Os formulários compartilham no frontend as validações de conveniência para e-mail e senha; mensagens de obrigatoriedade específicas de cada fluxo permanecem junto ao formulário. A validação do backend continua sendo a autoridade.

### Renderização e API

- Use estratégia híbrida; não force SSR dinâmico ou client-side para tudo.
- A página pública renderiza no servidor conteúdo inicial e metadados, como estabelecimento, serviços e profissionais.
- Agendamento e disponibilidade são Client Components interativos.
- Agenda, administração e financeiro são predominantemente client-side.
- Mantenha layouts e cascas estáticas como Server Components quando possível.
- Coloque `"use client"` na menor fronteira necessária; não marque o layout raiz sem necessidade.
- O navegador chama `/api/v1` diretamente; Caddy encaminha ao backend no mesmo domínio.
- Não crie BFF com Route Handlers nem use Server Actions para regras ou mutações.
- Server Components não chamam Route Handlers internos; uma leitura server-side legítima chama o backend Go diretamente.

### Estado

- Use estado, efeitos e Context nativos do React.
- Prefira estado local e eleve-o apenas ao ancestral necessário.
- Context serve somente a estado transversal, como sessão; não é cache genérico da API.
- Não adicione TanStack Query, Redux, Zustand ou equivalente sem nova decisão.
- O wrapper de `fetch` representa carregamento, sucesso, ausência e erro consistentemente.
- Cancele requisições obsoletas e impeça respostas antigas de sobrescrever estado recente.
